## Frozen references and numerical result

The standalone Python oracle uses 60-digit Decimal transfer/linear algebra and
exact Fraction authority for rational scope inputs. It derives matrices from
chromaticities/D65 using elimination; the separate JS candidate derives them
using a cofactor inverse. Both use the declared standards, not each other's
implementation. The oracle imports no production or candidate code. The
presentation oracle imports only that independent oracle. Expected values are
never regenerated by a comparison run.

The 68 final-view cases simulate binary16 storage between CPU operations.
They do not test Float32 arithmetic, GPU texture filtering, codec quantization
or every possible image. Their deliberate technical SDR shoulder is defined
in the frozen equations; it is not a finished artistic view transform or a
claimed implementation of BT.2390. Fixed coverage masks test text colors and
alpha; bundled-font/browser raster identity is still unmeasured. Plugin/effect
tests establish explicit rejection of old/unknown managed stages, not a new
compatible plugin ABI or reinterpretation of existing SDR effects.

The scope failure is material: 99.999, 100 and 100.001 nits all become
100.01318359375; 1,000 nits becomes 999.93359375, and 4,000 becomes
3999.734375. Reading a half-float buffer cannot recover those distinctions.
Scope collection before that storage boundary, or a separately versioned
precision-aware scope definition, is future research. No epsilon, new expected
bin, or relaxed threshold was introduced to make this candidate pass.

Provisional Decimal-only reference files remain in [rejected](rejected/README.md).
The discrete oracle was strengthened with exact rational arithmetic before
candidate evaluation; the rejected 4,000-nit representation happened to land
in the same capped bin, so it was not itself evidence of a wrong accepted bin.

## Next exclusive-slot request

Prepared, syntax-checked, **not executed**: [probe-codec.mjs](probe-codec.mjs).
Its exact hash is in `r1-r2-manifest.json`. Request one bounded R2 session for
three sequential 1024×16 I420P10 frames: one SDR709, one PQ2020, one HLG2020,
each a horizontal 0–1,023 luma ramp with neutral chroma. Requested encoder:
VP9 profile 2 / 10-bit / full range, 8 Mb/s, 30 fps, prefer software. Each cell
performs support/configure, one key-frame encode/flush, prefix inspection,
one same-browser decode/flush and raw luma comparison.

The script allows one live input/readback frame, one encoder/decoder per cell,
at most two returned packets / 4 MiB encoded bytes per cell, ≤1 MiB decoded
readback checked before allocation, and 10-second bounds for each asynchronous
flush/drain. It closes late frames and records any nonzero terminal owner count.
Three source plane buffers total 147,456 bytes over the sequential run; each
cell owns only 49,152 source bytes. Native codec allocations are unknown.
Encoded samples get fresh hashed artifact names. This is diagnostic luma
evidence, not a lossy-quality pass threshold or a complete chroma/metadata test.

Run only after an actual slot grant, from the issue worktree:
